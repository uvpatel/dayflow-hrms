# Dayflow HRMS — Implementation Plan

Last audited: 2026-08-22

## Current architecture

- Next.js 16.3 App Router application under `src/app`, using route groups for authentication and the authenticated dashboard.
- React 19 client screens use TanStack Query hooks in `src/hooks`; server mutations and reads are exposed through route handlers under `src/app/api/v1`.
- Better Auth 1.7.1 uses the Drizzle adapter with Neon PostgreSQL. Email/password, optional GitHub OAuth, verification callbacks, sessions, and the admin plugin are configured in `src/lib/auth.ts`.
- Server authorization is resolved through `src/lib/auth-context.ts` and the role/permission map in `src/lib/permissions.ts`.
- Domain code is separated into schemas, repositories, and services for employees, attendance, leave, approvals, organization, and payroll.
- Drizzle schemas live in `src/db/schema`; append-only migrations live in `drizzle`; development data is generated by `src/db/seed/index.ts`.
- The existing visual system uses Tailwind 4, shadcn/Base UI components, a warm neutral palette, compact information-dense dashboard layouts, and responsive sidebar navigation.

## Verified working surface

- Better Auth core tables contain the installed adapter fields, including `accountId`, `providerId`, `issuer`, access/refresh/ID tokens, expiry fields, password, and timestamps.
- Public signup defaults to employee and does not accept an elevated role.
- Dashboard layout performs a server session check and APIs call an authentication or permission guard.
- Employee, attendance, leave, approvals, payroll, organization, reports, notifications, and audit-log APIs and TanStack Query hooks already exist.
- Employee list/detail, attendance, time off, approvals, payroll, organization, reports, notifications, settings, and audit screens already exist.
- The baseline production build and TypeScript check pass. Permission tests pass. ESLint currently has warnings but no source compilation errors.

## Problems found

### Authentication and authorization

- Role values can diverge between Better Auth `user.role` and `employees.role`; normalization and role-change ownership need one source of truth.
- `getAuthContext` currently creates organizations and employee profiles during reads, which makes session resolution mutate state and can race.
- Employee numbers are generated randomly without a database uniqueness guarantee.
- Proxy protection only checks for a cookie; page-level role access is not consistently enforced.
- Email verification is configured but not required. The fallback development secret must never be accepted in production.
- Some handlers have a broad permission check but do not consistently scope manager requests to direct reports.

### Database and domain integrity

- Employee email/number, manager, department, designation, location, and work-schedule relationships lack several foreign keys and indexes.
- The manager relationship has no self/cycle validation and the seed does not assign direct reports.
- Attendance has no database constraint preventing duplicate daily/open records and stores calculated hours as text.
- Existing check-in accepts an optional client user ID and can act on the wrong identity; it does not calculate shift lateness, duration, overtime, or half-day status.
- Attendance corrections lack employee linkage, status, requested times, reviewer, decision comment, and audit-ready timestamps.
- Leave approval updates the request and allocation in separate operations; rejection comments are optional; cancellation and decision endpoints are missing.
- Payroll values are stored as text and several reports contain simulated totals/trends.
- Several supporting tables are skeletal and lack organization/employee relationships.
- The seed script labels itself idempotent but duplicates leave, attendance, notification, and audit rows on repeated execution. It also has only two managers and twenty total users rather than the requested staffing mix.

### Frontend and routing

- Legacy `/employee`, `/manager`, `/hr`, and `/admin` pages coexist with `/dashboard` and contain static or duplicate flows.
- The dashboard renders the same HR-oriented composition for every role and falls back to mock KPI/chart data.
- Sidebar visibility is not role-aware and several organization submenu links point to the overview rather than their intended routes.
- Missing canonical routes include `/dashboard/profile`, `/dashboard/my-team`, organization designations/locations/work-schedules, and manager team detail.
- Attendance UI does not consume a dedicated server-derived today state or display authoritative duration/schedule information.
- Some query mutations invalidate only their own domain rather than dashboard, reports, balances, approvals, and notifications.
- A number of pages have lint warnings, nested interactive elements, placeholder actions, or weak error/empty states.

### Documentation and tests

- Existing backend analysis documents do not match current code and required top-level API/schema/testing documents are absent.
- Current tests cover the permission matrix and auth schema only. Attendance, manager hierarchy, employee field restrictions, leave rules, and payroll locking need focused coverage.
- Database migration/seed execution cannot be verified safely until the configured URL is explicitly confirmed as a disposable development database.

## Implementation sequence

### 1. Auth and route security

- Normalize lowercase roles (`admin`, `hr`, `manager`, `employee`) in one module.
- Harden Better Auth secret/origin/rate-limit/email-verification configuration without breaking development email logging.
- Make auth context read-only and move employee onboarding/linking to explicit flows.
- Add page-level route policy helpers and canonical post-auth redirects without redirect loops.
- Enforce direct-report scoping in APIs in addition to permission names.

### 2. Schema and migrations

- Add safe foreign keys/indexes and uniqueness constraints for employees and manager/team access.
- Extend attendance and correction records with server-calculated duration/status fields and concurrency protection.
- Convert payroll amounts to PostgreSQL numeric columns using safe migration casts where possible.
- Generate append-only Drizzle migrations and inspect SQL; do not push/reset the database.

### 3. Domain services and APIs

- Implement server-authoritative, transactional attendance check-in/check-out and a today-state endpoint.
- Implement manager assignment with self/cycle prevention and team endpoints.
- Scope employee/attendance/leave/payroll reads to self, direct reports, or organization according to the role matrix.
- Implement leave cancellation and transactional approve/reject decisions with balance, notification, and audit updates.
- Remove simulated report values and aggregate actual persisted data.
- Keep route handlers thin and use consistent success/error envelopes.

### 4. Frontend integration

- Use a single `/dashboard` with employee, manager, HR, and admin variants backed by role-aware APIs.
- Add canonical profile and team routes; redirect legacy role landing pages.
- Make sidebar entries role-aware and repair active states/links.
- Add authoritative attendance state, live display-only duration, mutation disabling, and cross-domain query invalidation.
- Connect list filters and expose clear loading, error, retry, and empty states.

### 5. Seed, tests, and documentation

- Make seed writes idempotent and provide one admin, two HR users, three managers, at least twenty employees, real manager assignments, and representative workflow data.
- Add pure/domain tests for role scoping, manager cycles, attendance transitions/calculation, leave rules, and payroll visibility/locking.
- Update `README.md` and `.env.example`; create `API_DOCUMENTATION.md`, `DATABASE_SCHEMA.md`, and `TESTING.md`.
- Document that migrations and seed were generated but not executed unless the database is explicitly confirmed as development.

## Verification strategy

Run without touching external data:

```bash
bun run db:generate
bun run lint
bun run typecheck
bun test
bun run build
```

Run only after explicit confirmation of a disposable development database:

```bash
bun run db:migrate
bun run db:seed
```
